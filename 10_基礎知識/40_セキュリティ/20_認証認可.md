# 認証認可

- Cookie 認証/セッション
  - 認証成功後にサーバが、セッション ID を発行してCookie に載せて返却する
  - セッション情報は DB や Redis などのセッションストアで管理することが多い
  - ブラウザは以降のリクエストで Cookie を自動送信し、サーバはセッション ID を照合する
    - ◯: Cookie に HttpOnly や Secure を付けやすく、ブラウザ管理と相性がよい、通信量が比較的少ない
    - ×: サーバ側でセッション管理が必要、セッションストアへのアクセス負荷がある、セッションハイジャック対策が必要

- [JWT/トークン](https://www.jwt.io/ja)
  - 認証成功後にサーバが、ユーザ ID・有効期限・署名などを含む JWT(トークン)を発行する
    - クライアントは LocalStorage などに保存して Authorization: Bearer ヘッダで送る方式や、Cookie に保存して自動送信させる方式がある
    - サーバはトークンの署名や有効期限を検証し、必要に応じてリフレッシュトークンで再認証する
    - ◯: サーバ側でセッション照合が不要になりやすい、クレームを持たせて扱いやすい
    - ×: 誤って機密情報入れがち、通信量増えがち、期限変更が難しい、XSS の危険性

- [OAuth](https://ja.wikipedia.org/wiki/OAuth)
  - ユーザーの権限を第三者アプリへ安全に委譲するための認可の仕組み
